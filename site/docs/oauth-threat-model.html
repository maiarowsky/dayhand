    OAuth threat model

    On this page

    • Assets
    • Actors and trust boundaries
    • Threats and controls
    • Residual risks
    • Out of scope

    What the OAuth server (oauth.md) protects, from whom, how, and what is left. It covers /.well-known/*, /oauth/*, /connections*, the OAuth path of /mcp and the approval in the Android app. API keys, pairing and app JWTs are described in architecture.md and pairing.md.

    Assets

    • The owner's plan: tasks, history and settings, read and changed through /mcp.
    • Access and refresh tokens of agent connections, authorization codes, and the codes shown on the sign-in page.
    • The owner's decision: only the owner, on the paired phone, may let an agent in, and only with the scopes the owner chose.

    Actors and trust boundaries

    ActorTrusted with
    Owner with the paired phoneEvery decision; the app talks to app.* with its JWT
    Owner with an API key (dayhand)Listing and revoking connections (/connections*)
    Claude app, Claude CodeIts own tokens after approval; nothing more. Its name comes from its metadata document on https://claude.ai
    Any other MCP clientSame as Claude once approved, but its name is self-asserted (Dynamic Client Registration)
    Anyone on the internetNothing: every /oauth/* endpoint is open to them by design

    The browser that opens the sign-in page is not trusted: it proves nothing about who uses it. The phone is what makes a request legitimate.

    T1Code interception: an attacker gets an authorization code (a log, a redirect) and exchanges itPKCE S256 required (no plain, no request without it); the code is bound to client, redirect URI and resource, lives 2 minutes and dies on its first presentation, right or wrongoauth.test.ts: wrong verifier burns the code; code bound to client, redirect URI and resource

    T4Impersonation of Claude: a client calls itself "Claude"The phone says Identified by claude.ai only for a metadata document fetched from an allowed origin (default https://claude.ai only); a self-registered client is shown as Registered itself (its name is not verified). Names are cleaned of control and bidi characters and cut to 60Instrumented ConnectionsScreenTest, cleanName tests
    T5Consent phishing: an attacker opens the sign-in page with their own client and sends the owner the code ("type this in Dayhand")The code works only on the owner's phone and shows who asks and where the answer goes; a request older than 3 minutes gets a red warning; an answer to a program on the computer (loopback) gets a warning; the page and the app tell the owner to approve only a page they opened themselves. The approved code still goes to the page that asked, so the attacker must also hold the redirect URI: Claude's own callback, or a loopback on the attacker's machineConnectionsViewModelTest ("a request minutes old is flagged"), instrumented consent tests

    T8Refresh token theftRotation on every refresh; a rotated token used again more than 30 seconds later revokes the connection (both parties lose it, the owner sees it on the phone)"reusing a refresh token rotated long ago revokes the connection"
    T9Token for another server (confused deputy)Every token is bound to <issuer>/mcp (RFC 8707); /mcp refuses a token bound to anything else; resource must name /mcp when sent"a token issued for another resource (audience) gets 401"
    T10More access than grantedScopes tasks:read and tasks:write only; no broad default (a request without scope gets reading only); the phone may grant a part, never more; tools/list is filtered and other tools, user resources and prompts get 403 insufficient_scope; a refresh can only narrow"a read-only connection…", "a write-only connection…", "a refresh may narrow the scopes"
    T11Escalation from a connection: an agent mints API keys, pairs phones or approves itselfOAuth tokens work only on /mcp; /devices* and /connections* take API keys only; the approval needs the app's JWT; identity fields in tool arguments are refused"OAuth tokens cannot manage devices or connections"
    T12Revocation that does not biteA revoked connection's access and refresh tokens are refused on their next use, not when they expire"revoking a connection on the phone or with dayhand stops its tokens at once", RFC 7009 test
    T13SSRF through metadata URLsOnly URLs on DAYHAND_OAUTH_CIMD_ORIGINS (default https://claude.ai) are fetched; no redirects, 16 KB, 5 secondscimdUrlProblem tests, "metadata documents that are not acceptable…"
    T14XSS, clickjacking, CSRF on the sign-in pageEvery value is HTML-escaped; CSP default-src 'none' with a nonce for the one script and connect-src 'self'; frame-ancestors 'none', X-Frame-Options: DENY, form-action limited to the page and the redirect origin; the page's forms carry a 256-bit request handle, so a cross-site form cannot continue someone else's request"a client name is escaped on the page"

    Residual risks

    • Blocking Claude's published identity. The client_id of the Claude apps is public, so anyone can start 20 requests with it every 10 minutes and keep 5 waiting, which delays new Claude connections (not existing ones) for up to 10 minutes. The workaround is "Register automatically" (Dynamic Client Registration), whose client_id is private to that registration. The global flood guards (300 request starts per 10 minutes, 100 registrations per hour) can be filled the same way; npx convex run oauth:resetLimits clears them. Nobody gets access this way.
    • Consent phishing with a loopback client. An attacker who persuades the owner to approve a code, despite the warnings, gets a connection through a loopback redirect on the attacker's own machine. The warnings and the request's age are the only defence; the owner sees the connection under Agent connections and can disconnect it.
    • A stolen refresh token used within 30 seconds of the legitimate refresh is taken for a retry. The legitimate client's next refresh then fails, and a later use of an old token revokes the connection.
    • Metadata documents are fetched on every authorization request (no cache): at most 20 per client per 10 minutes, to claude.ai only.
    • Self-asserted names of registered clients can be anything printable; the app marks them as unverified.
    • Revoking an app JWT (a lost phone) takes up to an hour (pairing.md); during that hour the phone could still approve requests. Revoke the device with dayhand revoke.
    • Not tested against the real Claude apps before a production deployment: Claude reaches the server from Anthropic's network over public HTTPS. The flows are tested with a simulator (the MCP SDK's OAuth client and tests/oauthClient.ts) and on an emulator (android/scripts/e2e-connections.py).

    Out of scope

    Client secrets, confidential clients, the JWT bearer and client credentials grants, token introspection, OpenID Connect and sign-in on the web: Dayhand has no web accounts, and the paired phone is the only way in.
