    • URL: <deployment HTTP actions URL>/mcp, e.g. http://127.0.0.1:3211/mcp locally or https://<deployment>.convex.site/mcp on Convex Cloud.
    • Transport: Streamable HTTP, stateless, JSON responses (application/json); no SSE stream. Every message is one POST; notifications get 202; GET and DELETE get 405.
    • Protocol: 2026-07-28 and the 2025 revisions (2025-11-25, 2025-06-18, 2025-03-26, 2024-11-05) on the same URL; see Protocol versions.
    • Authentication: Authorization: Bearer <personal API key>, or an OAuth access token of an agent connection the owner approved on the phone, which is how the Claude apps connect (oauth.md). Missing, wrong, expired or revoked credentials get HTTP 401 with a WWW-Authenticate header that points OAuth clients at the authorization server. A request with a browser Origin header gets HTTP 403 unless the origin is listed in DAYHAND_MCP_ALLOWED_ORIGINS (deploy.md).
    • Every change is recorded with the key's kind as the actor (cli for the user at a terminal, agent for an AI agent) and the key's name, or as agent with the OAuth client's name; see Keys and actors.
    • Pass a clientId (e.g. a UUID) with changes you might retry; a repeated clientId is not applied twice. Pass dryRun: true to check a change without saving it (Dry runs).
    • Each key or connection may make 120 reads and 60 changes a minute (Limits).
    • Several agents can share the plan: an activity log, acceptance criteria and proof, dependencies and time-boxed claims; agents can ask the owner first, the owner can pause them or set a policy per tool, agents propose work into an inbox, and a health report shows what needs a look (agent-work.md).
    • The server's name and backend release version appear in serverInfo of initialize and _meta of 2026-07-28 results. The server identity is the source of truth; see Versions for release history.

    Tools

    The input schemas are generated from the same validators the operations enforce; the output schemas come from schemas/, the contract dayhand --json follows too.

    Every task has an id and a ref: the user's task number (1, 2, 3, …). It is given once, kept through the trash, the archive and a restore, and never given to another task, even after the task is purged. Every tool that takes a taskId accepts either the id or the number written as "#42".

    tools/list returns the tools in this order. Tools marked O are the owner's: only the app and cli keys may call them, and tools/list leaves them out for agents (agent keys and agent connections; since 0.11.0). Read-only tools are marked R, destructive ones D (destructiveHint); every change except add_task is idempotent (idempotentHint: repeating it with the same arguments changes nothing more), and no tool reaches outside Dayhand (openWorldHint: false). Each tool also has a title.

    Results

    A successful call returns the result as structuredContent (a list as { "result": [...] }, null as { "result": null }) and as JSON in its text block. A Markdown export's text block is the Markdown itself and its structuredContent is { "format": "markdown", "content": "…" }; an iCalendar export (format: "ics") likewise has the calendar text in both.

    Each tool's outputSchema is the result's schema from schemas/ or the tool error (anyOf), with every referenced schema inlined under $defs: clients never fetch a URL. The top level is an object, as 2025 clients require. backend/convex/lib/outputSchemas.ts is generated from docs/schemas by npm run schemas in backend/; a test fails when it is out of date.

    Finding tasks (list_all)

    ArgumentMeaning
    queryTasks whose title, note, resume note or labels contain this text, in any case
    statusOnly these statuses, e.g. ["todo", "doing"]; done tasks are included only when listed
    labelsOnly tasks having all of these labels
    readytrue: only tasks ready to work on (not done, no blockedReason, not a proposal, every task in dependsOn done); false: only the others
    proposedtrue: only proposals waiting in the inbox; without it, or false, proposals are left out (since 0.11.0)
    dueBefore, dueAfterOnly tasks due before / after this day (YYYY-MM-DD, "today", "tomorrow"); tasks without a day never match
    overduetrue: only overdue tasks; false: only the others
    includeDone, includeArchivedDone tasks (default true; ignored when status is given), archived ones (default false)
    limitPage size, 1 to 200
    cursornextCursor of the previous page

    Tasks come oldest due first (tasks without a day first, timed before untimed on one day). The result is { "result": [...], "total": <all matches>, "nextCursor": <string or null> }; pass nextCursor back as cursor with the same filters for the next page. The cursor is opaque and stays valid when tasks are added or removed in the meantime.

    Without limit, every match comes back at once and the text block holds the plain task array, as before 0.4.0, so clients that read the text keep working; with limit or cursor the text block holds the whole object.

    Agent work

    Since 0.10.0 a task may carry fields for agents working on it (agent-work.md has the reasons). None of them is a new status: the board stays todo, doing, done.

    FieldSet withMeaning
    acceptanceadd_task, update_taskCriteria { id, text, met } in order; new ones get a1, a2, …; the list is replaced as a whole, null or [] removes it (at most 50, up to 500 characters each)
    planadd_task, update_taskHow the work will be done (up to 20000 characters)
    proofcomplete_task{ summary?, links, checks: [{ name, result: "pass" | "fail", url? }] }, kept on the task (schema)
    dependsOnadd_task, update_taskIds of the tasks that must be done first (given as ids or "#42"); [] removes them; no cycles (at most 50)
    blockedReasonadd_task, update_taskWhy the task cannot go on; null clears it
    claimedBy, claimExpiresAtclaim_task, renew_claim, release_taskWho holds the claim (keyId or connectionId, and name) and until when (Unix ms); kept after expiry until released or claimed again

    When a task has acceptance criteria, an agent (an agent key or an agent connection) can complete it only when every criterion is met and the proof has a summary; otherwise complete_task (and set_status to done) fails with precondition_failed. The app and cli keys complete tasks as before. A repeating task's next occurrence keeps the criteria, unticked, and the plan.

    Claims

    claim_task gives the caller's key or connection the task for minutes (1 to 1440, default 120). While the claim lasts, another agent's claim_task, renew_claim, release_task and every change of that task (update_task, set_status, set_now, complete_task, reschedule_task, archive_task, delete_task, restore_task) fail with conflict, whose message names the holder and the expiry. Claiming again extends your own claim. renew_claim works while nobody else has claimed the task, also after your claim ran out; without a claim of yours it is precondition_failed. release_task ends the claim and saves note as the resume note. Completing the task ends its claim. Done, archived and trashed tasks cannot be claimed (invalid_argument). The owner wins: changes from the app and from cli keys are never refused, and the app can end any claim (app.release).

    Activity log (list_events)

    ArgumentMeaning
    sincenextCursor of an earlier call ("c…"), or a time as Unix milliseconds or ISO 8601 with a zone (the changes from then on); without it, the newest changes
    byOnly changes by app, cli, agent (any agent) or "agent: <name>"
    taskIdOnly changes of this task
    limit1 to 500, default 100

    The result is { "events": [...], "nextCursor": "c…", "hasMore": <bool> } (schema). Each event has id, at, taskId, ref and title (the task's now), action, actor, actorName, by, before and after, like a history entry. Events come oldest first, in the order the changes were committed. Pass nextCursor as since next time to get only what changed in between; hasMore: true means another page is already there. Only task changes are listed, not changes of API keys, webhooks or devices. Changes made before 0.10.0 appear once the deployment ran migrations:backfillEventSeqs (deploy.md).

    Approvals, pausing and policies

    Since 0.11.0 (agent-work.md has the reasons):

    • request_approval stores a request { action, detail?, options: [{ label, consequence?, id? }], reversible, expiresInMinutes? (1 to 10080, default 1440), taskId?, clientId? }; options get o1, o2, … unless they carry an id. The owner decides on the phone (or with a cli key, decide_approval); the agent reads the outcome with get_approval or gets the webhook approval.decided (webhooks.md). A request about a task enters that task's history and the activity log (approvalRequest, approvalDecide). Dayhand records the decision; it does not stop an agent from acting without one. The agent's own tooling has to check it.
    • pause_agents with paused: true refuses every change by an agent key or agent connection with agents_paused, dry runs included, until paused: false; reads keep working, and the owner's own changes (app, cli keys) are never refused.
    • set_tool_policy sets, for one agent key, allow, ask or deny on a tool that changes the plan, or on "*" (every such tool without its own rule); no rule means allow. deny fails the call with forbidden. ask fails it with approval_required and an approvalId: Dayhand has made a request with the options allow ("Allow once") and deny, bound to this key, this tool and these arguments (without clientId, dryRun and approvalId); calling again while it waits returns the same request. Once the owner allows it, the same call with approvalId runs once; another call, a second use, a denied or an expired request is refused. A dry run needs no approval. Policies are per API key; agent connections (OAuth) follow only the pause and their scopes.

    Proposals

    add_task with proposal: true adds a task with proposedAt: it waits in the owner's inbox and stays out of list_today, board, list_all (unless proposed: true), ready, the calendar feed and the phone's Today until the owner accepts it (accept_proposal), merges it into another task (merge_proposal: that task gets the proposal's note after a line naming it, its links, labels, source and return webhooks; the proposal goes to the trash with mergedInto) or rejects it (reject_proposal: to the trash). A proposal cannot be claimed, made the now task, moved to doing or completed (invalid_argument). Three fields work on any new task:

    FieldMeaning
    source{ kind, ref, url? }, e.g. { "kind": "sentry", "ref": "CHECKOUT-42" }. One source makes one task: add_task with a source that already made a task returns that task, also when it is in the trash; once the trash is purged the source is free again. A merged proposal's source leads to the task it was merged into
    requestedByWho asked for it (up to 200 characters); an agent's proposal without it says agent: <name>
    returnToId of one of the user's webhooks: it gets task.returned with the outcome (completed, rejected or merged) and the proof, whatever events it subscribes to (webhooks.md)

    Plan health (plan_health)

    plan_health (also GET /api/v1/health, dayhand health, the prompt plan_health) returns, as of at, in the user's time zone: agentsPaused; overdue, dueToday, inProgress (each with workingBy: "agent: <name>" while a claim lasts), expiredClaims, blocked (each with reasons: the blocked reason and every dependency not done yet), awaitingApproval (tasks with a pending request, and pendingApprovals in all), completedToday (each with proof, and withProof, withoutProof): each { count, tasks } with the first 20 tasks; proposals.count; and oldestOpen, the open task created longest ago with ageDays (schema). Proposals and archived tasks are not counted as open.

    Agent brief (agent_brief)

    agent_brief (also GET /api/v1/brief, dayhand prime --json) is what an agent reads first in a session, as of at and from its own side (since 0.12.0): every field of list_today, then caller (type, name), agentsPaused and pausedReason, policies (the owner's rules for the caller's own key other than allow), claims.active and claims.expired (each claim with claimedBy, claimExpiresAt and mine), approvals.pending (every request waiting, mine when the caller asked) and approvals.decided (the caller's requests decided in the last 24 hours, with the decision), ready (tasks ready to work on that no other agent holds, soonest due first), each { count, items } with the first 10; and nextSteps, sentences most pressing first that name the tools and the phase guides to use (schema). While agents are paused, nextSteps says only that.

    Backlog.md (import_backlog, export_backlog)

    import_backlog takes files: [{ path, content }], with paths relative to the backlog folder; export_backlog returns the files and configuration to write. The result contracts are backlog-import and backlog-export. See backlog-md.md for field mappings, source identity, limits, approvals and safe folder handling.

    Dry runs

    Every changing tool takes dryRun: true. The change runs with every check, then Dayhand rolls it back: nothing is saved and nothing enters the history. The result is what the real call would return, marked "dryRun": true (for set_now with taskId: null, { "result": null, "dryRun": true }). A dry run of add_task shows the number the task would get, but does not reserve it. A change that would fail fails its dry run with the same error. Dry runs count as changes for the limits.

    Limits

    Each API key, and each agent connection (OAuth), may make 120 reads and 60 changes a minute (convex/callLimits.ts). The minute starts with the first call; reads and changes are counted apart. Reads are tool calls of read-only tools, resources/read of dayhand://today, dayhand://activity… and dayhand://tasks/…, and prompts/get; listing tools, resources and prompts, server/discover, dayhand://guide and the dayhand://workflow/… guides are not counted.

    A call over the limit is refused before it runs, so nothing is applied:

    • a tool call returns the tool error rate_limited with retryAfterMs, HTTP 200 and a Retry-After header (seconds);
    • resources/read and prompts/get get HTTP 429 with Retry-After and the JSON-RPC error { "code": 429, "message": "Too many reads with this API key: …", "data": { "retryAfterMs" } }.

    npx convex run callLimits:reset '{"keyId":"<key id>"}' clears a key's counters ('{"connectionId":"<connection id>"}' a connection's).

    Repeat rules

    repeat is an object, or an RFC 5545 RRULE string (with or without RRULE:) that the server reads into the object. Every repeating task also comes back with its rule as an RRULE in rrule, e.g. "FREQ=WEEKLY;BYDAY=MO,TH".

    FieldMeaningRRULE
    every, intervalevery day, week, month or year; interval 2 = every other (1 to 366)FREQ, INTERVAL
    weekdaysweekly rules: days 1 (Monday) to 7 (Sunday)BYDAY=MO,TH
    monthDaymonthly rules: day 1 to 31, or -1 for the last dayBYMONTHDAY=15, BYMONTHDAY=-1
    weekdayOfMonthmonthly rules: { nth, weekday }, nth 1 to 5 or -1 (last) to -5BYDAY=2TU, BYDAY=-1FR (or BYDAY=TU;BYSETPOS=2)
    from"due" (default): the next date follows the due date; "completion": it is counted from the day the task is donenone
    untillast date the series may fall on, YYYY-MM-DDUNTIL=20261231 (a UTC date-time is read in the user's time zone)
    countoccurrences left, this one included; 1 = the last oneCOUNT

    until and count cannot be combined (as in RFC 5545). Completing a task counted from the due date creates the first date of the series after today, so a late completion skips the dates it missed, and those count against count. When the series has ended, complete_task returns next: null. The next occurrence keeps the title, note, labels, links and reminders, with the checklist unticked.

    Dayhand reads FREQ (DAILY, WEEKLY, MONTHLY, YEARLY), INTERVAL, BYDAY, BYMONTHDAY, BYSETPOS, UNTIL, COUNT and WKST; anything else (BYHOUR, BYMONTH, …) is an invalid_argument naming the part. Where Dayhand differs from RFC 5545:

    • A day the month does not have (31 in April) falls on the month's last day; RFC 5545 skips the month. rrule writes such days as BYMONTHDAY=28,29,30,31;BYSETPOS=-1, which means the same in both, and reads that form back as monthDay: 31. A plain BYMONTHDAY=31 is read as monthDay: 31 too, with Dayhand's meaning.
    • A plain monthly rule takes its day from the due date; after a shorter month the next occurrence keeps that day as monthDay (31 Jan, 28 Feb, 31 Mar).
    • A yearly rule from 29 February falls on 28 February in other years and stays there.
    • from: "completion" has no RRULE form; rrule describes the dates only.
    • Weeks start on Monday; another WKST is refused only where it would change the dates (several days every two or more weeks).

    The rule logic is in backend/convex/lib/repeat.ts (advance, and occurrences to list a series ahead, e.g. for a calendar) and lib/rrule.ts (toRRule, parseRRule).

    Checklists and reminders

    • checklist: items { id, title, done } in the order shown. update_task replaces the whole list: send the items you keep with their ids, new items without one (the server gives c1, c2, …). null or [] removes it. At most 100 items of up to 500 characters. History records the list before and after each change.
    • reminders: the task's own reminders instead of the default ones from settings. Each is { minutesBefore } (before the due time; rings only for timed tasks) or { time: "HH:MM", daysBefore? } (that time on the due day, or up to 30 days before; works for untimed tasks too). A task without reminders uses the defaults; [] means no reminders for this task; null in update_task goes back to the defaults. At most 5. Reminders ring on the phone (architecture.md).

    Protocol versions

    One endpoint serves both eras of MCP, the way the specification describes a dual-era server:

    • 2025 revisions (2025-11-25 and earlier): the client sends initialize, and the server answers with the requested version when it knows it, otherwise 2025-11-25. ping works. Results have no resultType. Dayhand keeps no session, so every request stands alone anyway.
    • 2026-07-28: no initialize; a request is served as 2026-07-28 when its params._meta carries io.modelcontextprotocol/protocolVersion. It must also carry io.modelcontextprotocol/clientCapabilities (else -32602, HTTP 400) and the headers MCP-Protocol-Version (equal to that version), Mcp-Method and, for tools/call, prompts/get and resources/read, Mcp-Name (plain or =?base64?…?=), all matching the body (else -32020, HTTP 400). server/discover returns supportedVersions (both eras), the capabilities and the instructions. Every result has resultType: "complete" and _meta["io.modelcontextprotocol/serverInfo"]; server/discover, tools/list, prompts/list, resources/list and resources/templates/list carry ttlMs: 300000 and cacheScope: "public" (tools/list of an agent, or of a token with fewer scopes: private, since it leaves tools out), resources/read carries ttlMs: 0 and cacheScope: "private" (dayhand://guide: public). ping no longer exists and unknown methods get HTTP 404.

    Not offered in either era: subscriptions/listen (and listChanged notifications), logging, completion, sampling, elicitation and the tasks extension. Dayhand never asks the client for input, so no request returns input_required.

    The official TypeScript SDK v2 reaches the 2026-07-28 era with versionNegotiation: { mode: "auto" } (or a pin); without it, it speaks 2025 like SDK v1. Both are tested (backend/tests/mcp-modern.test.ts).

    Keys and actors

    Every API key has a name and a kind:

    • cli: the user at a terminal. History shows changes as cli.
    • agent: an AI agent. History shows changes as agent: <key name>, e.g. agent: claude-code.

    Changes made in the app are app. Changes made through an agent connection (OAuth, e.g. the Claude app) are agent with the client's name, e.g. agent: Claude (oauth.md). get_task returns each history entry with actor (app, cli or agent), actorName (the key's or client's name, null for the app) and by, the label above. Give each agent its own key so it can be told apart and revoked on its own.

    Keys without a kind (created before 0.3.0) act as agent keys; the 0.3.0 migration records that (deploy.md). A new key is an agent key unless created with "kind": "cli":

    npx convex run apiKeys:create '{"userId":"<issuer>|owner","actor":"app","name":"macbook","kind":"cli"}'
npx convex run apiKeys:create '{"userId":"<issuer>|owner","actor":"app","name":"claude-code"}'

    The app does the same with app.createApiKey({ name, kind }); app.listApiKeys returns each key's kind.

    Since 0.8.0 a key also has a scope and may expire:

    ScopeOn /mcpREST /api/v1 (api.md)Account: keys, webhooks, devices, connections, calendar feed
    readonly the reading tools (tools/list shows only them; a change gets 403 insufficient_scope)GET routesno (403)

    Keys without a scope (every key made before 0.8.0) are full keys; nothing changes for them. expiresAt (Unix milliseconds) ends a key: after it the key gets 401 like a revoked one.

    npx convex run apiKeys:create '{"userId":"<issuer>|owner","actor":"app","name":"n8n","scope":"read","expiresAt":1798761600000}'

    Creating and revoking API keys is not an MCP tool on purpose: a key that can mint keys could outlive its own revocation. Keys are managed by the app (app.createApiKey, app.revokeApiKey), by the deployment admin (npx convex run apiKeys:create), or with a full key through POST /api/v1/keys (dayhand key create). A key made that way can only have scope read or write, expires no later than the key that made it, and works only while that key works: revoking the parent stops it too (api.md).

    Phone pairing is not an MCP tool either. The CLI pairs phones through separate endpoints (/devices/*, see pairing.md) that accept the same API key.

    Connecting a client

    The Claude apps (claude.ai, Desktop, Android, iOS) add Dayhand as a custom connector with the URL <deployment HTTP actions URL>/mcp and sign in with OAuth; the owner approves the connection on the phone. The steps are in oauth.md.

    Any MCP client with Streamable HTTP and custom headers works with an API key, for example:

    claude mcp add --transport http dayhand http://127.0.0.1:3211/mcp \
  --header "Authorization: Bearer $DAYHAND_API_KEY"
