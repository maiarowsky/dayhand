    Dayhand has no hosted service and no accounts of its own. Your plan lives on your devices and on a server you run, and nothing in Dayhand sends it anywhere else. This page says what is stored where, which secrets exist and how they are protected, what the agent controls can and cannot do, and how to report a problem. The detailed threat models are linked at the end.

    Where your plan is

    PlaceWhat it holdsWho can read it
    Your server (a Convex deployment)the whole plan, its history, settings, hashes of keys and tokens, webhook secrets, the calendar addressyou, and anyone with admin access to that deployment: your Convex account, or your computer for the local server
    The Android appits copy of the plan and the waiting changes; the sign-in, encrypted with a key in the Android Keystorethe phone; Android's cloud backup and device transfer are off for Dayhand
    Dayhand for macOSits copy of the plan in ~/Library/Application Support/Dayhand; the sign-in in the login Keychainyour Mac user
    Dayhand for Linuxits copy in ~/.local/share/dayhand; the sign-in in the Secret Service keyringyour Linux user
    dayhand and dayhand uino offline plan or outbox; shell completion caches task numbers, titles and labels; the key is in the system keychain, or a file only you can readyour user on that computer
    Backups and exportswhatever you export: dayhand export, the phone's backup file, npx convex exportwherever you keep them

    Shell completion writes tasks-<hash>.json in the CLI cache folder: ~/.cache/dayhand (or $XDG_CACHE_HOME/dayhand) on Linux, ~/Library/Caches/dayhand on macOS, or %LOCALAPPDATA%\dayhand\Cache on Windows; DAYHAND_CACHE_DIR overrides it. The folder is created with mode 700 and files with mode 600 where POSIX permissions apply. The 60-second lifetime controls freshness, not deletion: cached titles and labels remain on disk until you remove the cache files.

    The local server (dayhand server start) keeps its data and keys in a private folder (mode 700, files 600) and listens on 127.0.0.1 only. A server on your Convex account runs on Convex's infrastructure, in your account; Convex can technically reach it, as any host can reach what it hosts.

    No tracking

    • The Android app has no analytics, no crash reporting and no other outside services. It talks only to your server.
    • Dayhand for macOS and Linux talk only to your server. A macOS build made with the release key also checks the update feed (Sparkle), with Sparkle's system profile off; builds you make yourself never do.
    • dayhand talks only to the server you signed it in to. dayhand server start downloads the Convex local backend from Convex's GitHub releases once, at a pinned version whose checksum it checks.
    • This website sets no cookies and loads nothing from other servers.

    Keys and tokens are long random values compared in constant time; error answers never say whether a code or token existed, expired or was revoked. A key never goes into config.toml: dayhand login keeps it in the macOS Keychain, the Windows Credential Manager or the Secret Service, or in a file readable only by you when there is none. The keychain keeps the key out of dotfiles and shell history; it does not hide it from programs running as you.

    Who may do what

    • Scopes. An API key reads (read), also changes tasks and settings (write), or also manages keys, webhooks, devices, connections and the calendar feed (full). A key made with another key is read or write and never outlives its parent.
    • Owner tools. Deciding approval requests, pausing agents, tool policies and accepting, merging or rejecting proposals are for you only: the apps and cli keys. Agents do not see these tools and are refused when they call them.
    • Agent controls are checked inside the same transaction as the change, for MCP and the REST API alike, so there is no way around them through another surface (agents).
    • Limits. Each key and each OAuth connection may make 120 reads and 60 changes a minute.
    • What Dayhand cannot do: stop an agent from acting outside Dayhand. An approval is a record the agent is expected to respect; enforce it in the agent's own tooling as well.

    The server's doors

    • /mcp refuses requests from a browser page (an Origin header) unless you allow that origin, and answers a missing or wrong credential with 401.
    • The REST API has no CORS: other websites cannot call it from a browser, and OAuth tokens do not work there.
    • Webhooks are sent only to public HTTPS addresses: local, private, link-local and reserved addresses are refused when the webhook is added and again before each delivery, and redirects are not followed (webhooks).
    • OAuth sign-ins return only to the Claude apps' documented addresses, with PKCE, and every connection is approved on your phone (OAuth threat model).

    Good habits

    • Give every agent and integration its own key, with the smallest scope and an expiry. Revoke it when it is no longer used (dayhand key list, dayhand key revoke).
    • A key can pair a phone, and the phone keeps working after the key is revoked: when a key may have leaked, revoke it and also check dayhand devices.
    • Lost a phone or a laptop: dayhand revoke <deviceId>. Its app token still works for up to an hour.
    • Treat the calendar address like a password. If it was shared, make a new one (dayhand calendar rotate).
    • Keep the copy of the app-signing key in a password manager, or delete it; the deployment holds the one in use. Keep backups and exports out of shared folders: they contain your plan.
    • Keep the backend up to date: git pull and dayhand server deploy (or start) again (updating).

    Reporting a problem

    Report security problems privately, never in a public issue, pull request or discussion: open the repository's Security tab on GitHub and choose Report a vulnerability. Only the maintainers see the report. Say what is affected, how to reproduce it and the impact you expect; leave out real keys and other people's data. You can expect an acknowledgement within 7 days and an assessment within 30 days. The full policy: SECURITY.md.
